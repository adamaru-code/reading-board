# 文字入力の不具合を防ぐ確認手順

2026-10-04、1 冊に「1」と「１」のタグを付けると保存に失敗する（500）不具合があった（#271 → PR #272）。
原因は **DB とアプリで「同じ文字」の考え方がずれていた**こと。ユーザーが入力する文字を扱う機能を作る・直すときは、次の 1〜5 を確かめる。

## 1. DB が「同じ」とみなす違いを知っておく

MySQL の照合順序 `utf8mb4_0900_ai_ci`（このプロジェクトの既定）は、次を**同じ文字列**として比べる（2026-10-04 に開発 DB で確認）。

| 違い | 例 |
|---|---|
| 大文字・小文字 | `Ruby` = `ruby` |
| 半角・全角 | `1` = `１`、`IT` = `ＩＴ`、`カナ` = `ｶﾅ` |
| ひらがな・カタカナ | `はな` = `ハナ` |
| 濁点・半濁点 | `ハ` = `パ` |
| 丸数字など | `①` = `1` |

迷ったら、その場で DB に聞いて確かめる（思い込みで書かない）。

```bash
cd backend && bin/rails runner 'c = ActiveRecord::Base.connection; puts c.select_value("SELECT #{c.quote("1")} = #{c.quote("１")} COLLATE utf8mb4_0900_ai_ci")'
```

このため：
- **UNIQUE な列**（`tags.name`・`users.email` など）には、DB が同じとみなす 2 つの値は**共存できない**（2 つ目は `RecordNotUnique`）
- `WHERE name = ?`・`find_by(name:)`・`LIKE` の検索は、これらの違いを**無視して当たる**（キーワード検索が半角でも全角でも当たるのはこのため）

## 2. アプリの比較とずれる所を探す

Ruby の `==`・`uniq`・`include?`・`Set`、JavaScript の `===`・`includes` は**文字が完全に同じときだけ**同じとみなす。DB と考え方が違うので、次の形を探す。

| 形 | 起きること | 例 |
|---|---|---|
| アプリで重複を除いてから、DB の UNIQUE な組み合わせに入れる | アプリでは別、DB では同じ → **UNIQUE に当たって 500** | `tag_names=` が `%w[1 １]` を別扱い → 同じ `Tag` を 2 回つなげて `book_tags` の UNIQUE に当たった（#271） |
| `find_or_create_by(name:)` で探してから作る | 既にある方が見つかる → **入力と違う書き方で表示** | 「２０２６年」と入れたのに「2026年」と出る |
| アプリで文字を比べて「同じ・違う」を決める | DB では同じなのに別のものとして扱う | CSV 読み込みの重複チェック（タイトル＋著者）が Ruby の文字比較で、「第2版」と「第２版」を別の本として足していた → `WEIGHT_STRING` で DB の比べ方にそろえた（#281） |
| 名前を書き換えて「同じ名前ならエラー」 | DB では同じ → 付け替え先が自分自身になる | タグの管理で it → IT（#274 で管理者だけ書き換えにした） |

確認のコマンド（文字を比べている所を洗い出す）：

```bash
grep -rn "\.uniq\|to_set\|include?\|find_or_create_by\|\.strip ==" backend/app
grep -rn "includes(\|=== " frontend/src --include='*.vue' --include='*.ts' | grep -v __tests__   # zsh では --include の * を引用符で囲む（囲まないと no matches found）
```

## 3. そろえ方

- **書き方をそろえる（正規化）**：Unicode の **NFKC** を使う。全角英数字 → 半角、半角カナ → 全角、① → 1、Ⅱ → II になる
  - Ruby：`name.to_s.unicode_normalize(:nfkc).strip`（タグは `Tag.normalize_name`）
  - JavaScript：`name.normalize('NFKC').trim()`（`TagInput.vue`）
  - **バックエンドとフロントの両方で同じ方法**にする（フロントだけだと API・CSV から入る値がそろわない）
  - **「数字以外を消す」処理の前にも NFKC をかける**。`gsub(/[^0-9Xx]/, "")` は全角の「９７８…」を数字と見なさず全部消すので、全角で書いた ISBN が空になっていた（`OpenbdClient.normalize`。2026-10-05、PR #282）。ISBN・電話番号・郵便番号などの欄を作るときは、テストに全角数字を入れる
- **Rails の `normalizes`** をモデルに書く：保存するときだけでなく、`find_by(name:)` / `where(name:)` で探すときも同じようにそろえる（`Tag`・`HiddenTag`）
- **NFKC でもそろわない違い**（大文字・小文字、ひらがな・カタカナ、濁点）は、DB が同じとみなす。アプリ側では「DB で探した**レコード**で重複を除く」（`cleaned.map { find_or_create_by }.uniq`）。文字列で `uniq` しない
- **レコードが無い文字列どうしをアプリで比べるしかない**とき（CSV の行どうしなど）は、DB に `WEIGHT_STRING(? COLLATE utf8mb4_0900_ai_ci)`（MySQL が比べるときに使う重み）を出させ、それをキーにして比べる。重みが同じなら DB の `=` でも同じ（`BookCsvImporter#comparison_keys`）
- 大文字・小文字などを**区別して保存したい**ときは、列の照合順序を変える（`utf8mb4_0900_as_cs` など）。影響が大きいので、変える前にユーザーと相談する

## 4. 今あるデータもそろえる（マイグレーション）

- 正規化を足したら、**今あるデータも同じ方法でそろえる**データのマイグレーションを書く（`20261004120000_normalize_tag_names`）。そろえた結果が別の行と同じになるならまとめる
- **流す前に、確認用データで試す**（quality-review §1.7）。ただし DB が同じとみなす値は UNIQUE な列に**共存できない**ので、「① と 1 を両方入れて試す」はできない（2026-10-04、試そうとして `Duplicate entry` で止まった）。そろっていない書き方で 1 つ入れて、そろうことを確かめる
- 本番は次の AWS 起動時に流れるので、確かめる項目をメモリの「次に AWS を使うとき」に足す

## 5. テストに入れる文字

文字を保存・比較・検索する機能のテストには、次の組を入れる。

| 組 | 確かめること |
|---|---|
| `１` と `1`、`ＩＴ` と `IT`、`ｶﾅ` と `カナ`、`①` と `1` | 全角で入れても半角で保存される／1 つのレコードに両方付けても失敗しない |
| `it` と `IT`、`はな` と `ハナ`、`ハ` と `パ` | DB が同じとみなすので、重複として扱われる（500 にならない） |
| 前後の空白・全角スペース | 取り除かれる |
| `%`・`_` | LIKE 検索で「何にでも当たる」にならない（`sanitize_sql_like`） |

## 6. 画面の文言

- 断るときは、使う人に分かる理由を書く（例：「書き方（大文字・小文字など）だけの変更は、管理者だけができます」）
- **作る側の事情（共有テーブル・照合順序）を画面に書かない**。「ほかの人の本のタグは変わりません」は使う人を迷わせた（2026-10-04、PR #270 で外した）
