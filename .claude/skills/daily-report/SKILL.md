# 日報と再発防止の確認

ユーザーは作業の終わりに「再発防止ができているか確認して、できていなければしてから日報を」と頼む。
手順が決まっていなかったため、2026-10-01 は詰まったこと 4 件のうち 3 件が作業ログにしか無く、スキルに書かれていなかった。
**日報を頼まれたら、頼まれ方が短くても次の 1〜5 を必ず順に行う。**

## 1. 詰まったことを全部集める

次の出どころを上から見て、その日の「詰まったこと」を漏れなく書き出す（同じ原因のものは 1 件にまとめる）。

- 会話の中で起きたこと：
  - CI・テスト・lint・型チェック・Brakeman などが**一度でも落ちた / 警告が出た**
  - ユーザーの「上手くいかない」「分かりにくい」「違う」、画面確認で NG の番号が出た
  - こちらの案や判断を**あとで変えた**（ユーザーが判断を変えた、計算し直して結論が変わった など）
  - あとから**直し忘れ・見落とし**に気づいた（docs の古い言葉、別の PR で直した所 など）
  - 外部サービス・GitHub・AWS の不具合や想定外の動き
- その日の作業ログ（メモリの `progress-<日付>.md`）の「学び」「詰まった」と書いた所
- **こちらの誤り**：確かめずに状態を伝えた、決まりを守らなかった、謝った・訂正したこと（ユーザーに指摘されたものも含める）

## 2. 再発防止が書かれているか検索して表にする

1 件ずつ、キーワードで次の場所を検索する（読んだ気にならず、必ずコマンドで探す）。

```bash
cd /Users/ada/RaiseTech/reading-board
grep -rn "<キーワード>" .claude/skills/ CLAUDE.md docs/aws-deploy-guide.md
```

結果をユーザーに表で見せる（✅＝書かれている／△＝近いことはあるが今回の場合が書かれていない／❌＝書かれていない）。

| # | 詰まったこと | 再発防止 |
|---|---|---|
| 1 | Brakeman の版が古いだけで CI が落ちた | ✅ quality-review §1.7（#234） |
| 2 | 既存の SQL 片の埋め込みを Brakeman が指摘 | △ ルールはあるが、この場合が無い |

- **△ も足りないものとして扱う**（ルールが一般的すぎて、次も同じ書き方をしてしまったから詰まった）
- 作業ログ（メモリ）にだけ書いてあるものは ❌ と同じ（メモリはリポジトリのスキルほど確実に読まれない）

## 3. 足りないものを書き足す（Issue → PR）

置き場所は内容で決める。

| 内容 | 置き場所 |
|---|---|
| コード・テスト・セキュリティ・docs・CI・PR の書き方 | `.claude/skills/quality-review/SKILL.md`（該当する章） |
| ユーザーにお願いする画面確認の出し方 | `.claude/skills/ui-check-steps/SKILL.md` |
| サーバーの起動・ポート | `.claude/skills/enforce-default-ports/SKILL.md` |
| Issue・ブランチ・PR・マージの流れ | `CLAUDE.md` |
| AWS の起動・停止・確認 | `docs/aws-deploy-guide.md` |
| ユーザーへの話し方・説明の好み（このリポジトリに限らないもの） | メモリの feedback（リポジトリには書かない） |

- 書き方：**何が起きたか → どう見分けるか → どう直す・どう避けるか**を短く。最後に日付と PR 番号（例：`2026-10-01、PR #236`）。具体的なコマンド・ファイル名・エラーメッセージを入れる
- 流れは CLAUDE.md どおり：Issue（`[Chore] <日付> の学びを品質チェックのスキルに追加` など）→ ブランチ → PR → CI → マージ → Issue が閉じたか確認。複数のスキルにまたがっても 1 つの Issue・PR にまとめてよい
- ユーザーは「再発防止してから日報」と頼んでいるので、足りないものがあれば**確認を取らずに書き足してよい**（何を足したかは表と一緒に伝える）
- 再発防止にしないもの：その日だけの作業（確認用データの削除など）、すでに直して二度と起きない一回きりの誤字

## 4. 作業ログ（メモリ）を更新する

`progress-<日付>.md` に、再発防止で足したこと（Issue・PR 番号）と終了状態（main のコミット・未マージの PR・開いている Issue。**書く直前にコマンドで確かめる**）を書き、`MEMORY.md` の 1 行も直す。

## 5. 日報を出す

日報の前に、2 の表と 3 で足したことを伝える。日報は次の形で**簡潔に**、初学者にも分かる言葉で書く（用語には意味を添える）。

**日報は全体を 1 つのコードブロックに入れたプレーンテキストで出す**。ユーザーは日報をコピーして貼り付ける。Markdown の番号付きリスト（`1.` で始まる行）は、表示のときに番号が飾りとして描かれるので、選んでコピーしても番号が付いてこない（2026-10-06、「箇条書きの数字がコピペできない。不便」と言われた）。コードブロックなら書いたとおりの文字が残り、右上のコピーボタンで全体を取れる。

- 見出しは `【学習内容】` のように書く。`**太字**` や `##` は使わない（コードブロックの中では記号がそのまま出る）
- 番号（`1.`）と `- ` は、そのまま文字として書く
- 次回の候補（作業ログに残したもの）は、コードブロックの中の最後に `【次回やること】` として入れる

~~~markdown
```
日報

日付：YYYY-MM-DD

【学習内容】
- やったこと（PR 番号）を 1 行ずつ

【詰まったこと】
1. …
2. …

【解決方法】
1. …（「詰まったこと」と同じ番号で対応させる）
2. …

【気づき・学び】
- 次に活かせる形で（「〜するときは〜する」）

【次回やること】
- …
```
~~~

- 再発防止の表・サーバーの止め方・コマンドは、日報のコードブロックの**外**に普通の Markdown で書く（日報に混ぜない）
- サーバーについて書くときは、**書く直前に** `lsof -i :3000 -sTCP:LISTEN`・`lsof -i :5173 -sTCP:LISTEN`・`lsof -i :3306 -sTCP:LISTEN` で確かめ、**動いているものだけ**止め方（Rails・Vite は Ctrl+C、MySQL は `docker compose stop`）を書く。前の返事の「動いたままです」を流用しない（2026-10-01、確かめずに書いて、実際は止まっていた。CLAUDE.md §9）
